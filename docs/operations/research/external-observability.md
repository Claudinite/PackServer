### 1.1b Outside log services with free plans, as general app-log store vs. as a tamper-evident audit sink

Question from the owner: should an outside log service with a free plan hold the audit log, so a compromised Worker cannot edit it? The requirements for an *audit sink* differ from those for app logs: (1) the credential inside the Worker must be **write-only** (cannot query, delete, or change retention); (2) deletion or retention shortening must need a credential the Worker never holds; (3) ideally a **provider-side retention lock** (WORM) so that even an account-level operator mistake cannot delete within the window; (4) retention ≥ 1 year (the architecture's `audit_log` is the record of publish/security actions); (5) **verifiability**: a hash chain or Merkle log with periodically published heads, so removal or reordering is detectable even by a party that does not trust the operator ([transparency.dev verifiable data structures](https://transparency.dev/verifiable-data-structures/)).

**Assessment.** No free-plan log service offers a retention lock. What they do offer is a *write-only credential* (Axiom basic token, Grafana `logs:write` policy, New Relic license key, Sentry DSN), which already defeats the main threat (a compromised Worker editing or deleting history), because the Worker never holds a credential that can delete. The residual risks are: the vendor *account* (owner login, PATs) being compromised; retention expiring silently (Grafana 14 d, Sentry/New Relic 30 d, Better Stack 3 d) and, with a write-only key, the Worker can still **append forged entries**; append-only protects the past, not the authenticity of new entries.

**Recommended shape (cheap, defensible):**
1. Keep the designed D1 `audit` database as the queryable copy (separate database, separate binding; the trust-boundary split means only the admin Worker reads it).
2. Every audit event is also appended, in `ctx.waitUntil`, to **one external write-only sink**. Pick **Axiom** (free 1 TB; basic ingest-only token per dataset; set the `audit` dataset retention to Forever on Axiom Cloud, $25/mo, or accept the default on the free plan and rely on step 3 for the archive) or **New Relic** (free 100 GB, no-delete policy, 30 d). This is the near-real-time witness and the place to alert on audit anomalies (publish spikes, MFA disables) independently of Cloudflare.
3. **Hash chain + R2 bucket lock as the archive**: each audit row carries `prev_hash` and `hash = sha256(prev_hash || canonical_json(row))`; an hourly cron Worker writes the hour's rows as one JSONL object to a locked R2 bucket (write-only token/binding; lock indefinite or ≥ 1 year) and writes the chain head `{ts, seq, hash}` to the external sink *and* to a GitHub release/issue comment or a Sigstore Rekor entry (free, independent of both Cloudflare and the log vendor). Any deletion or reorder in D1 or R2 breaks the chain; any rewrite of R2 is blocked by the lock; and the published heads let a third party verify ([design pattern](https://www.designgurus.io/answers/detail/how-do-you-design-tamperevident-audit-logs-merkle-trees-hashing); [Rekor monitoring precedent](https://blog.trailofbits.com/2025/12/12/catching-malicious-package-releases-using-a-transparency-log/)).
4. Treat the log vendor account like a production secret: hardware-key MFA on the owner login, no PAT anywhere, ingest token scoped to the `audit` dataset only, token expiry + rotation, alert on token creation in the vendor's own audit log (Axiom has an audit-log feature; verify on the free plan).
5. Cost: $0 (Axiom free or New Relic free) + R2 pennies; $25/mo if Axiom Cloud "Forever" retention is wanted in the queryable copy.

For **general app logs** the same free tiers are fine and the choice is governed by §1.1 (Axiom or Grafana Cloud); do not mix the audit dataset with app logs so that retention trims on the noisy dataset never touch it.

## 2. Modern practice

### 2.1 SLOs, error budgets, multi-window multi-burn-rate alerting
Google SRE Workbook ch. 5 ("Alerting on SLOs") is still the reference; the Grafana write-up reproduces the two paging tiers for a 99.9 % SLO: burn 14.4 over 1 h with 5 m confirmation (2 % of monthly budget in 1 h), burn 6 over 6 h with 30 m confirmation (5 % in 6 h); ticket tiers (burn 3 over 1 d / 2 h, burn 1 over 3 d / 6 h) come from the Workbook. Condition = `(long AND short)` per tier, tiers OR'd; short window stops alerts firing long after recovery ([Grafana, Feb 2025](https://grafana.com/blog/2025/02/28/how-to-implement-multi-window-multi-burn-rate-alerts-with-grafana-cloud/); [OneUptime burn-rate note, 2026](https://oneuptime.com/blog/post/2026-02-20-monitoring-alerting-best-practices/markdown)).
Low-traffic caveat (relevant to PackServer at launch): with <~1 req/s, a 5-min window on a 99.9 % SLO contains too few requests for 14.4× to be meaningful; the Workbook's options are to lengthen windows, lower the SLO, or synthesise traffic (synthetic checks count toward the SLI). Practical choice for PackServer v0: 99.5 % availability SLO on the read path (index/metadata/download), 99 % on publish, burn-rate alerts only on the read path until traffic justifies more.
Suggested SLIs per the architecture: (a) **download/metadata availability** (`/api/packs/*`, `cdn.packserver.dev`): non-5xx and <1 s; (b) **MCP endpoint**: successful tool calls; (c) **publish pipeline freshness**: time from upload to `published` state (Workflow), target p95 < N min; (d) **auth success** (passkey/GitHub login). Cloudflare's own Alerts product now supports SLO-type rules (other note), so the burn-rate rules can live either there or in Grafana.

### 2.2 RED / USE / golden signals
RED (rate, errors, duration) per Worker route is the natural fit for a request-serving registry; USE (utilisation, saturation, errors) applies to the few stateful parts: D1 (writes/s vs single-writer limit, DB size vs 10 GB cap), Durable Object quotas, Workflow queue depth, Sandbox concurrency, AI Gateway token spend. Golden-signal saturation for PackServer is mostly *quota* saturation (Workers CPU ms, D1 writes, R2 Class A, Anthropic token budget) rather than hosts.

### 2.3 OpenTelemetry semantic conventions
- **HTTP** server/client conventions are stable (`http.request.method`, `http.response.status_code`, `url.path`, `server.address`, `http.route`); use `http.route` (the Hono route pattern) not `url.path` as the metric dimension to keep cardinality bounded.
- **GenAI** (`gen_ai.*`) is **still "Development" status as of Jul 2026**; moved to a separate `open-telemetry/semantic-conventions-genai` repo (Jun 2026, v1.42). Key names: `gen_ai.operation.name`, `gen_ai.provider.name` (replaces `gen_ai.system`), `gen_ai.request.model`, `gen_ai.usage.input_tokens`/`output_tokens`; metrics `gen_ai.client.token.usage`, `gen_ai.client.operation.duration`; prompt/completion content is **opt-in** (`gen_ai.input.messages`, …) and the old `gen_ai.prompt` was removed. For the validator's LLM review, emit these names on the span around the AI Gateway call and expect renames ([dev.to summary, Jul 2026](https://dev.to/azena-ai/opentelemetrys-genai-semantic-conventions-are-not-stable-yet-heres-what-actually-shipped-in-2026-3mke); [Dash0 explainer, Sep 2026](https://www.dash0.com/knowledge/opentelemetry-genai-semantic-conventions-explained)). AI Gateway's own logs already give per-request tokens/cost; the span should carry the AI Gateway log id for correlation.

### 2.4 Structured logging with trace correlation; wide events ("observability 2.0")
Charity Majors' position: the one real difference between o11y 1.0 and 2.0 is a **single source of truth** of wide, structured, high-cardinality events from which metrics and traces are derived at read time; cost is controlled by sampling rather than by stripping cardinality, and the question to ask a vendor is "how many times do you store my data?" ([charity.wtf, Nov 2024](https://charity.wtf/p/there-is-only-one-key-difference-between-observability-1-0-and-2-0); [GreptimeDB wide-events note, Jun 2026](https://greptime.com/tech-content/2026-06-10-wide-events-observability-2-0)). Stripe's "canonical log line" is the same idea in log form.
For Workers this is natural: a Hono middleware builds one JSON object per request (route, status, duration, `trace_id`, `worker_version` from the metadata binding, colo, principal kind, scope, pack id/version, cache status, D1 ms, R2 ms, Stripe/GitHub call outcome, validation verdict, risk score, token counts) and emits it once via `console.log` (picked up by Workers Logs and the OTLP log destination) in `ctx.waitUntil`. Include `trace_id`/`span_id` from the runtime trace so logs and traces join. Columnar stores (Axiom, Honeycomb, ClickHouse-based) price this well; per-event indexers (Datadog) and label-indexed stores (Loki) do not.

### 2.5 Synthetic vs RUM
Synthetic checks give availability from outside with known cadence and are the only thing that observes "the site is down" when the Worker never runs; RUM (Web Vitals from real browsers) covers the public site/UI only. For a registry whose clients are CLIs, CI and agents, RUM is low value; synthetic checks that exercise the *real client flows* (index fetch → download → hash verify; MCP initialize → search; publish dry-run on a staging scope) matter more. Grafana's or Checkly's free tiers cover 3–4 such checks at 5-min cadence; put at least one check on a provider that is **not** Cloudflare-hosted.

### 2.6 Alert fatigue and solo on-call
Consistent advice across the SRE Workbook and 2026 write-ups ([OneUptime](https://oneuptime.com/blog/post/2026-02-20-monitoring-alerting-best-practices/markdown), [solo-builder on-call](https://blog.vibecoder.me/on-call-practices-solo-builders)):
- Page only on **user-visible symptoms** (SLO burn, synthetic failure, payments broken, publish pipeline stalled); causes (CPU, quota at 80 %) go to a daily digest.
- Three tiers: **page** (phone/Pushover, 24×7, must be actionable), **notify** (Slack/email within hours), **digest** (weekly). Demote any alert that fires twice without requiring action.
- Every alert carries `runbook_url`, impact statement and first command to run; keep runbooks as one-page markdown in the repo (`docs/runbooks/*.md`) and link by stable URL.
- Weekly review of alert counts; auto-resolve warnings; group by service+alert name with a 5-min window.
- Solo specifics: publish support hours; no escalation exists, so **auto-remediation and safe defaults replace a second responder** (e.g. automatic rollback of a gradual deployment on burn-rate breach, circuit-breaker to disable LLM review when AI Gateway errors, cache-serve-stale for metadata). Keep a "break-glass" checklist for Stripe webhooks and GitHub App key rotation.

### 2.7 Registry-specific monitoring
Signals that other registries' incidents show matter (sources in §2.8):
| Concern | Signal to record / alert | Precedent |
|---|---|---|
| Package integrity | `sha256` mismatch between R2 object and `pack_versions.sha256` on serve (sample 1 % of downloads + every publish); client-reported hash mismatches via a `/report` endpoint; alert on **any** mismatch (critical) | npm/TanStack 2026: malicious versions served for hours; integrity checks are the last line |
| Signature / provenance verification | count of OIDC exchanges rejected by claim (repo, workflow, env), provenance attestation verification failures per publisher, publishes **not** from the declared workflow step | TanStack postmortem: publish came from an unexpected step of the workflow; recommends publish-source verification and per-publish review ([TanStack, May 2026](https://tanstack.com/blog/npm-supply-chain-compromise-postmortem)); Trail of Bits Rekor monitoring of identities ([Dec 2025](https://blog.trailofbits.com/2025/12/12/catching-malicious-package-releases-using-a-transparency-log/)) |
| Abuse / spam publish spikes | publishes per account per hour, new scopes per day, version churn per pack, name-pattern reuse (edit distance to existing names), file-hash reuse across packs; alert at N× 7-day baseline | npm IndonesianFoods: thousands of templated packages unflagged because heuristics looked at payload not volume ([Snyk, Nov 2025](https://snyk.io/blog/automated-package-publication-incident-indonesianfoods/)); GitHub Packages outage 2025-08-14 caused by a publish spike exceeding capacity ([GitHub status](https://www.githubstatus.com/incidents/fg0pp1nl4bdg)) |
| Malware / validation outcomes | validation verdict distribution per day (pass/flag/reject), LLM-review disagreement rate with static checks, quarantine count, time-in-quarantine, moderator queue age, validator Workflow failure rate and Sandbox timeouts | ClawHub found 341/2,857 skills malicious by plain-language instruction (from registry-trust research) |
| Takedown latency | time from report → quarantine → removal; alert if > 1 h for `security` reports | TanStack: removal depended on npm acting server-side, took hours |
| Account takeover | login from new country + token mint within 10 min, MFA disable events, passkey removal, token use after `last_used_at` gap > 90 d | 2025–26 npm/crates.io/Open VSX incidents were account takeovers (architecture README) |
| Capacity | publish queue depth, D1 write rate vs. limit, Sandbox concurrency, Anthropic spend/day vs. budget (hard stop) | PyPI 2025-04-08 outage fixed by adding worker-pool capacity ([status.python.org](https://status.python.org/incidents/tg6dd9n4nrrx)) |

### 2.8 How public registries monitor and handle incidents (verified from code/status pages)
- **PyPI (Warehouse)**: `requirements/main.in` pins `sentry-sdk` and `datadog>=0.55.0`; `warehouse/config.py` wires `sentry.dsn` and a `metrics` backend (statsd/Datadog). Public incidents on status.python.org (e.g. Simple/JSON API outage 2025-04-08, ~37 min, capacity added; "PyPI uploads failing"; backend partial availability 2026). Incident posts are short; root causes rarely published.
- **crates.io**: `Cargo.toml` on `main` depends on `opentelemetry`, `opentelemetry-otlp`, `tracing-opentelemetry`, `json-subscriber` (JSON logs with trace context) — i.e. OTel/OTLP, no Sentry crate found today. Metrics pipeline: `rust-lang/crates-io-heroku-metrics` turns Heroku log drains into Prometheus via Vector on ECS ([repo](https://github.com/rust-lang/crates-io-heroku-metrics)). Status via statusgator/isdown aggregators; no formal postmortem page found.
- **RubyGems.org**: `Gemfile` has `datadog ~> 2.44`, `dogstatsd-ruby`, `honeybadger` (errors). status.rubygems.org publishes incidents (search degradation 2026-02-12, 2h15m, cause unstated; "elevated errors", "partial outage" entries). Their 2013 compromise postmortem is still the canonical registry postmortem ([blog.rubygems.org 2013](https://blog.rubygems.org/2013/04/06/postmortem.html)).
- **npm**: incidents on githubstatus.com with one-paragraph RCAs (2025-08-14 publish-spike outage: "adding guardrails… updating runbooks"). Security incidents (Shai-Hulud 2025–26, TanStack 2026) were detected by **third-party researchers within ~20–30 min**, not by registry alerting — the lesson for PackServer is to alert publishers on their own publishes (email/webhook per publish, like npm's publish notifications) and to make takedown fast.
Takeaway: the big registries run Datadog/Sentry/OTel like any web app; the registry-specific value is in publish-event auditing, publisher notifications and takedown speed, not in exotic tooling.

## 3. Monitoring canary / gradual releases

| System | Mechanism | What to borrow |
|---|---|---|
| **Kayenta / Spinnaker ACA** | Baseline and canary deployed side by side; per-metric **Mann-Whitney U** test at 98 % confidence with ±25 % tolerance around the Hodges-Lehmann estimate; metrics classified Pass/High/Low/Nodata; group score = % pass; summary score vs. `pass` (e.g. 90) / `marginal` (75) thresholds; `critical` metrics zero the score; ≥50 % Nodata fails ([Spinnaker judge docs](https://spinnaker.io/docs/guides/user/canary/judge)) | The statistical core: compare distributions, not point values; require a minimum sample; make error rate and hash-mismatch "critical" metrics |
| **Argo Rollouts AnalysisTemplates** | `AnalysisTemplate` with `successCondition`/`failureCondition` over Prometheus/Datadog/NewRelic/Web/Kayenta providers; `interval`, `count`, `failureLimit`; `stable-hash`/`canary-hash` passed as args to scope queries ([Argo Kayenta integration](https://argo-rollouts.readthedocs.io/en/latest/analysis/kayenta/)) | Template shape: metric query parameterised by version id; N consecutive intervals; failure limit then rollback |
| **Flagger** | Per-step weight increase with built-in `request-success-rate` and `request-duration` checks plus custom `MetricTemplate`s; threshold count of failed checks triggers rollback ([Flagger/Flux guides 2026](https://oneuptime.com/blog/post/2026-03-13-how-to-implement-automated-rollback-based-on-custom-metrics-with-flagger/markdown)) | Simple threshold gates are enough at low traffic; statistical judges need thousands of samples per window |

**Mapping to Cloudflare gradual deployments** ([CF docs](https://developers.cloudflare.com/workers/versions-and-deployments/gradual-deployments/)): `wrangler versions upload` → `wrangler versions deploy` with a percentage split (from the last 100 versions); **version overrides** let you hit the new version before it has traffic (the "self-test" hook); **version affinity** pins a client to one version; Durable Objects run only one version (so DO-backed quotas/locks cannot be canaried, deploy them with `wrangler deploy` after the stateless Workers), Workflows/cron are not addressed in the docs (treat as all-or-nothing). Observability per version: the **version metadata binding** gives `id`/`tag`/`timestamp` to stamp every wide event, Logpush carries `ScriptVersion`, and Workers Logs can be filtered by version in the dashboard (other note covers details). There is no built-in judge; the loop is: deploy 5 % → wait for N requests per version → compare `error_rate`, `p95 duration`, `hash_mismatch`, `5xx by route` between `version=new` and `version=old` over the same window (same colos, same minute buckets to remove time effects) → promote or `wrangler rollback`. At S (10M/mo ≈ 4 req/s), a 5 % canary sees ~0.2 req/s, so expect to wait ~1–2 h for a 1 % error-rate difference to be detectable; use 10–25 % steps and route-level success rate rather than latency percentiles early on. GitHub Actions can run this as a job that queries the backend (Grafana/Axiom API) and calls `wrangler versions deploy`/`wrangler rollback` — the same shape as Argo's `count`/`interval`/`failureLimit`.

The owner's "traffic duplication with wet-run on old / dry-run on RC and diff of recorded external calls" is not what Kayenta/Argo/Flagger do (they compare *metrics*, not recorded I/O). The closest precedents are **shadow/dark traffic** (Diffy at Twitter, Flagger's mirroring step, Envoy request mirroring) plus a request/response recorder; on Workers this would be a Worker that `fetch`es both versions via version overrides / service bindings, with the RC bound to a recording layer around D1/R2/KV/Stripe/GitHub that returns the old version's recorded responses instead of writing. It is feasible but is a product to build, not to buy; flag for the design agent and confirm intent with the owner.

## 4. Privacy: PII and IP addresses in logs

- **IPs are personal data** for an operator with a realistic route to identification (CJEU *Breyer* C-582/14, 2016; reaffirmed as a relative test in *SRB* C-413/23 P, 2025). Treat all IPs as personal data ([ComplyDog summary](https://complydog.com/blog/is-an-ip-address-personal-data); [ccdcoe on Breyer](https://ccdcoe.org/incyder-articles/cjeu-determines-dynamic-ip-addresses-can-be-personal-data-but-can-also-be-processed-for-operability-purposes/)).
- **Legal basis**: legitimate interest (Art. 6(1)(f)) with **Recital 49** explicitly naming network/information security (abuse, DoS prevention) — but only with a documented balancing test, purpose limitation and storage limitation ([ctrl.blog](https://ctrl.blog/entry/gdpr-web-server-logs); [last9 GDPR log guide](https://last9.io/blog/gdpr-log-management/)).
- **Retention**: no statutory number; common practice is 7–30 days for raw access logs with IPs, longer only for aggregated or pseudonymised data; delete from backups too. Cloudflare's own retention defaults (7 days free / up to 1 year paid "coming soon") must be configured deliberately per dataset.
- **Redaction practice**: don't log raw IPs in application wide events — store a **keyed hash with a daily-rotating salt** (`ip_hash`, as the architecture's `audit_log.ip_hash` already does) or truncate (/24, /48) and note truncation alone is weak when combined with other fields; never log tokens, session ids, email addresses, Stripe PANs (Stripe never gives them anyway), webhook bodies, or pack contents; redact `Authorization`, `Cookie`, `X-Api-Key` headers in any request-capture; keep raw IPs only in the security dataset (WAF/rate-limit events) with the shortest retention. Sentry: enable `sendDefaultPii:false` (default) and scrub `request.headers`, `user.ip_address`.
- **Vendor side**: every third-party backend is a processor → DPA, region selection (Grafana/Axiom/Honeycomb/Sentry/New Relic all offer EU regions; New Relic charges +$0.05/GB for EU), and sub-processor list in the privacy policy. Logpush/OTLP destinations should be EU endpoints if the user base is EU-heavy.
- **Right to erasure**: a hashed/truncated IP + no user id in wide events means logs are out of scope for DSARs; the audit log (user ids) needs a documented retention (e.g. 1 year for publish/security actions, justified by Recital 49).

## 5. Recommendation shape (cost-anchored)

| Layer | Pick | Monthly cost S / L |
|---|---|---|
| Runtime traces + logs (zero-code) | Cloudflare OTLP destinations → **Grafana Cloud** (free) or **Axiom** (free/$25) | $0 / no CF export charge + $25–220 backend |
