# Security review of the monitoring plan (2026-10-22)

Scope: an adversarial read of [../monitoring.md](../monitoring.md) (v0, 2026-10-22) against the architecture summary and the two research notes under [../research/](../research/). The questions asked: what telemetry leaks, who can forge or read it, how the gate judge and the synthetic tenant can be turned against the owner, which credentials the plan introduces and whether each is least-privilege, whether an attacker can run up the telemetry bill, what the retention and hashing design means under GDPR, and which security events the plan does not watch at all. Every High and Medium finding, and the cheap Lows, were applied to `monitoring.md` in the same change; the status column says what was done. The release plan and test plan the monitoring plan cites are not in this repository, so findings that touch them are recorded as notes for those threads rather than fixed here.

Severity: High means an attacker could force a security-relevant outcome (page the owner at will, roll back a release, reach a retired version, read secrets) or a clear privacy breach; Medium means a real weakness that needs a design change but requires more than one step or an unlucky configuration; Low means hygiene.

## Notes

The plan's own redaction list (§3.4) is good and the biggest leaks were in platform features it did not account for rather than in its own fields: invocation logs with full URLs, `db.query.text` in D1 spans and `Logs[]` in the Logpush trace-events dataset. All three are documented in the Cloudflare research and the fixes are configuration, so they were cheap to add.

The gate judge is the component most worth attacking because it converts telemetry into a deploy decision. Three independent paths let an outsider influence it (client-reported mismatches, a client-settable synthetic flag and the version override header). The fixes keep `source = all` usable at launch, because the synthetic arm is now populated only by server-verified prober traffic, and they change the response to a manipulated gate from rollback to halt. The release thread should still decide whether a halted rollout at 25% is an acceptable state for an attacker to be able to cause.

The synthetic tenant was the second real privilege problem. The plan already keeps the prober off the write path for everything except the hourly dry-run publish from GitHub Actions; the review tightens that one path so the tenant can never put bytes on the CDN.

Two factual flags were added rather than resolved: whether Cloudflare honours the version override header for unauthenticated requests, and whether Logpush Transformers can compute a keyed hash. Both are in the research as gaps and the plan now says what to do until they are checked.

Items left for other threads: the release plan should own the WAF rule for the override header and the public response header format (MS-03), the architecture thread should confirm the `admin.action` and `token.rejected` signals exist in the audit producer so monitoring can read them (MS-11), and the test plan needs the probe-safe tag to require that a scenario can never write to a public bucket (MS-05).
