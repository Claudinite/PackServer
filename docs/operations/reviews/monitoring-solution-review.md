# Solution review of the monitoring plan (2026-10-22)

Reviewed: [docs/operations/monitoring.md](../monitoring.md) (v0, 2026-10-22) against the architecture README, the two research notes under `docs/operations/research/`, the hosting cost estimate and the agreements recorded with the release and test threads. Cloudflare claims marked "verified" below were checked on developers.cloudflare.com on 2026-10-22; where a page could not be fetched the claim keeps the plan's own "unverified" flag. This review recommends only; it does not edit monitoring.md because the security review is editing it at the same time. The status column was added when the recommendations were applied later the same day: every one is applied, some with a different mechanism than proposed, and the §3 arithmetic below is the reviewer's and is superseded where R6 changed the Worker request volume (see monitoring.md §14).

## 1. Verdict

The plan is sound in its shape and better than most v0 monitoring plans: one wide event per request with OpenTelemetry field names, Analytics Engine as the metrics substrate, a cron Worker that answers named gates per version, a witness off Cloudflare, pages that link runbooks, an explicit low-traffic strategy, privacy rules enforced by a unit test, and a cost model. The research behind it is careful and the plan keeps the research's "unverified" flags honestly. The audit-trail answer in §5 is correct and consistent with the architecture thread.

It is over-built in three places for a product run by one person at launch, and it has one set of correctness problems that would produce wrong verdicts or wrong bills if implemented as written.

Over-built:

1. Every page-severity alert is to be implemented twice, once as a Monitor and once in the gate judge, with "the same SQL". For a solo owner that is two rule sets to keep in step, and the stated reason (Monitors is beta) is already covered by the dead-man's switch and the witness. The judge should be the single evaluator for pages; Monitors should be used only where the judge cannot do the job cheaply (anomaly detection) and as a backup for three or four alerts, not all fifteen.
2. Seventeen gates, fifteen pages and eighteen runbooks before launch. `gate.availability` and `gate.error_rate` are the same number from different ends, `gate.exceptions` overlaps both, and `page.canary_rolled_back` and `page.llm_budget` page a human about something the system already handled. A launch set of about seven gates and ten pages is enough; the rest can be phase 5 to 7 work.
3. A separate alert-router Worker, a separate prober Worker and a separate judge Worker. The router and the judge can be one Worker (one deployable, one set of secrets, one heartbeat); the prober can stay separate because it runs the test DSL.

Correctness problems to fix before the plan is implemented (details in the table):

- The canary statistics are too loose at the floors the plan sets. At 300 samples a relative guard of "2x baseline and 0.5 points absolute" trips on 3 errors, which a healthy canary with a 0.2 percent baseline produces 2.3 percent of the time per evaluation, and the judge evaluates every minute over a sliding window, so a false fail per release is close to certain. A p99 over 1,000 samples is the ten slowest requests. The plan should require a minimum count of bad events, require the failure to persist across consecutive evaluations, and gate on p95 at launch.
- The claim that Monitors' SLO mode "is multi-window burn rate" is not what the product does. It triggers when availability is below one target in both windows. Burn-rate tiers can be built on it, but only by giving each tier its own monitor with the target set to `100 - burn_rate × (100 - SLO)`.
- One of the two `quantileExactWeighted` spellings is wrong, and the judge's query budget is understated by one to two orders of magnitude.
- The §9.3 synthetic-load design assumes a candidate can be reached through the version override header before it receives traffic. The version overrides page says the override "will only be applied if the specified version is in the current deployment", so the candidate must be in the deployment first (at a small or zero split, which the release plan must confirm is possible).
- The cost table omits Logpush Transformer charges for the IP-hashing job (about $1.50 a month at mid and $15 at 10x, a third of the stated 10x total) and inherits a wrong OTLP export price from the external research.
- The plan's mid-scale traffic figure (19M Worker requests a month) is the hosting estimate's update-check traffic, but the plan also states that the CDN host has no Worker. Both cannot be true; the sample-size table, the log volumes and the Analytics Engine point counts all depend on which one is.

None of this changes the recommendation of a Cloudflare-native stack at launch. Grafana Cloud or Axiom as a second console would not be a better answer for one person; the plan's reasons for deferring them hold. The right move is to trim the launch scope and fix the numbers.

## 3. Corrected arithmetic

Pro zone $25 a month billed monthly ($20 annual). Health Checks on Pro: 10.

### 3.2 Canary statistics (§9.2, §9.3)

- Relative guard at the 300-request floor, baseline 0.2 percent: the guard trips at 3 bad events (0.7 percent is 2x plus 0.5 points). P(3 or more | Poisson 0.6) = 2.3 percent per evaluation. Baseline 0.5 percent: trips at 3 (1.5 percent); P(3 or more | 1.5) = 19 percent. Absolute 1 percent threshold at 300 requests with a true 0.5 percent rate: P(4 or more | 1.5) = 6.6 percent. Evaluated every minute over a sliding window these per-look rates compound; hence R1.
- Two-proportion z-test at 95 percent, 1 percent versus 2 percent: power about 45 percent at 1,000 per arm, about 100 percent at 10,000 per arm. The plan's "once both arms have over 1,000 samples" should read 10,000.
