None. The MCP endpoint lists public packs only. A private pack is fetched by cn in the member repo's GitHub Actions workflow, which proves the repo's org with the Actions OIDC token against the pack's org allowlist (see private pack access). No token is stored anywhere.

Required before you can publish. Other accounts may enable it for extra protection. Passkeys are recommended; an authenticator app is the fallback.

Why we require this for publishers. Packs add guards, checks and scheduled tasks to every repo that declares them. A compromised publisher account could ship a malicious version to every one of those repos on its next update PR.

Auto-publish from GitHub

Publish a new version every time you push a matching tag. No long-lived tokens: GitHub Actions proves its identity with OIDC (trusted publishing).

1 · Repository

Trusted publisher: googlecloudplatform/claudinite-packsOptional read-only GitHub App: installed
Monorepos: one connection per pack path.

2 · Trigger

The tag is the version read from pack.json (e.g. 1.61021.1); a second build on the same day bumps the build number (1.61021.2).
Tags on other branches are ignored.

3 · Trusted publishing identity

We accept publishes only from this exact workflow identity. Anything else is rejected, even with a valid tag.

Workflow to add

Commit as .github/workflows/publish.yml. The id-token: write permission is what makes OIDC work.

name: Publish pack
on:
  push:
    tags: ["1.*"]
permissions:
  id-token: write
  contents: read
jobs:
  publish:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: .claudinite/bin/cn vendor packs/gcp-ops/
        # the archive is the vendored set (test/, docs/ stripped)
      - uses: packserver/publish-action@v1
        with:
          path: packs/gcp-ops/
          # no token needed: OIDC

Superseded. The owner chose (2026-10-22) an allowlist of GitHub orgs per private pack; cn proves its repo's org with the GitHub Actions OIDC token, so no read token is stored. The options below are kept as the earlier comparison; the calm prototype and flows.md §10 show the chosen model.

Access follows organization membership. Everyone in Google Cloud can read the pack; optionally narrow to teams synced from GitHub.

@googlecloudplatform/sre ×@googlecloudplatform/oncall ×

A repo's update task authenticates with an org member's own read token, so access is revoked automatically when someone leaves the org.

Trade-offs

+ Simplest mental model; offboarding is automatic.
+ Maps to how enterprises already manage GitHub.
– No way to share with a customer or contractor outside the org.
– Requires mirroring GitHub teams to be useful at scale.

Grant access to specific PackServer accounts by handle or email, inside or outside your org. Like sharing a document.
